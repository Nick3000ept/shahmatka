### Защита от сдвижки строк (chk)
Фронтенд шлёт с каждой строкой отпечаток `chk:{c:corpus,f:floor,w:work}`. Бэкенд (saveRows/saveAll) перед записью сверяет B/C/F целевой строки с отпечатком; не совпало (лист отсортировали/вставили строки) → строка НЕ пишется, её rowId возвращается в `mismatched[]`. Фронтенд оставляет такие строки в MOD и просит обновить страницу и сохранить заново.

### Надёжность сети — fetchJson
Все загрузки и сохранения идут через `fetchJson(url, opts)`: до 3 попыток с паузой 1.2с/2.4с при сетевых ошибках и HTML-ответах GAS. HTML-ответ на сохранение после всех попыток трактуется как «вероятно записано» (тот же parseWarn, что раньше).
| POST | `addTask` | Добавляет одно поручение (легаси, фронтенд использует `addTasks`) |
| POST | `addTasks` | Пакет поручений ОДНИМ запросом: валидация всех строк, одна запись setValues — либо весь пакет, либо ничего (требует `pwd`) |
| POST | `updateTask` | Обновляет поручение по id: статус/текст/срок/комментарий/приоритет (требует `pwd` = пароль админа) |
| POST | `saveProtocol` | Пишет протокол в лист «Протоколы» (№/Дата/Автор/Содержимое), автонумерация; требует `pwd` |
| GET | `getContractorEmails` | Лист «Подрядчики»: A=название, E=email → items[{name,email}] |
| GET | `getSysPresets` | Системные пресеты фильтров из листа «Пресеты» → {presets:{имя:конфиг}} |
| POST | `saveSysPreset` | Создать/обновить системный пресет (имя+конфиг JSON в лист «Пресеты», upsert по имени); требует `pwd` |
| POST | `deleteSysPreset` | «Удалить» системный пресет: очищает ячейки строки (deleteRow не используем — правило «строки скриптом не удалять»); требует `pwd` |
| POST | `sendProtocol` | Строит PDF из preamble + sections, шлёт каждому получателю отдельное письмо (MailApp, отправитель — аккаунт GAS); при `tg:true` дублирует PDF в Telegram-чат (Bot API sendDocument); отметка в столбце E листа «Протоколы»; требует `pwd` |
| POST | `sendTgNotify` | Текстовое сообщение в Telegram-чат (запрос актуализации); длинный текст режется на части ~3500 символов; требует `pwd` |
| POST | `setTgConfig` | Разовая настройка Telegram: пишет токен бота и id чата в Script Properties (`TG_BOT_TOKEN`, `TG_CHAT_ID`); требует `pwd` |

> **Поле `pp` в любом POST (2026-09-15):** если оно есть — сначала проверяется пропуск портала; нужен годный с ролью
> `администратор`, иначе `{ok:false, error:'bad_pass'}` и ничего не пишется. Годный пропуск заменяет `pwd` во всех
> действиях с пометкой «требует `pwd`», а автор записи (`author` запроса и `author` каждой строки `rows`) — ФИО из пропуска.
> Без `pp` — всё как раньше.

### Поручения (лист «Поручения», создаётся автоматически)
Столбцы: `A=id | B=Подрядчик | C=Текст | D=Срок | E=Статус (открыто/выполнено) | F=Создано | G=Автор | H=Комментарий | I=Приоритет ('' | Высокий)`.
Фронтенд: панель справа (кнопка «📋 Протокол»). **С 2026-08-04 панель видна всем**: не-админ (просмотр, подрядчик) получает только список ручных поручений для чтения — без формы создания, без правки комментариев, без кнопок «Выполнено» и «Сформировать протокол» (форма и кнопки под классом `admin-only`, элементы управления в `taskItemHtml` рисуются только при `IS_ADMIN`). Пароль админа хранится в sessionStorage (`sb3_admin_pwd`) и передаётся в POST; на `sb3.acons.space` вместо пароля уходит пропуск портала `pp` (`portalPP()`, проверка наличия — `hasAdminAuth()`); если у админа их нет — панель сама запрашивает вход (у просмотра пароль не спрашивается).
- **Комментарий к поручению** (2026-08-04): заполняется админом вручную — поле под текстом при создании поручения и редактируемое поле у каждого открытого поручения в списке (сохраняется при уходе из поля, `saveTaskComment` → `updateTask`). У выполненных показывается только для чтения (💬). В протоколе комментарий добавляется к строке поручения в скобках после срока. Заголовок H у существующего листа дописывается автоматически (`ensureTasksSheet_`).
- **Форма добавления переработана** (2026-08-04): «Тема» (input, одна строка) + «Описание»
  (textarea 2 строки, авторасширяется по тексту — `autoGrowComm`), **без даты и подрядчика**;
  кнопка «📄 Сформировать протокол» — внизу панели, под списком поручений (org теперь необязателен и на бэке —
  addTask/addTasks требуют только текст; поручения без подрядчика идут в «Общие» в протоколе).
  Кнопка «＋ Добавить»: optimistic UI — поручение сразу появляется в списке (временный id
  `tmp…`), форма очищается под следующее, запрос уходит фоном, `loadTasks` подменяет
  временную запись настоящей; при ошибке — запись убирается, текст возвращается в форму.
  Клики по ещё сохраняющемуся поручению (`tmp`-id) вежливо отбиваются. Мультистрочная
  форма с автодобавлением строк удалена (`protOrgOptions`/`protRowInput`).
- **Приоритет поручения** (2026-08-04): значок «!» в правом верхнем углу карточки
  (`.ti-pri-ico`) — клик переключает обычный ↔ «Высокий» (`toggleTaskPriority` →
  `updateTask`, столбец I; заголовок дописывается автоматически). Высокие — наверху
  списка (сортировка в `renderTasksList`), карточка с красной полосой слева, значок
  залит красным; у не-админа значок виден только у высоких, не кликабелен. Кнопка
  «✓ Выполнено» — по вертикальному центру карточки. Optimistic UI: список
  перестраивается мгновенно, запрос уходит фоном, при ошибке — откат.
- **Комментарий — автовысота** (2026-08-04): поле комментария — `textarea`, высота
  подстраивается под текст (`autoGrowComm`, при вводе и после отрисовки списка) —
  длинные комментарии видны целиком.
- **Оптимизация скорости/надёжности** (2026-08-04):
  - Все запросы поручений идут через `fetchJson` (3 ретрая, распознавание HTML-ответа GAS).
  - Сохранение новых поручений — пакетом одним POST `addTasks` (раньше: цикл `addTask` по одному → риск «половина записалась» и дублей при повторе).
  - Список открытых поручений кэшируется в localStorage (`sb3_tasks`): панель показывает его мгновенно, свежий подтягивается фоном. Кэш обновляется после загрузки, «выполнено» и правки комментария.
  - По умолчанию грузятся только открытые (`getTasks` без `all=1`); выполненные подгружаются при первом раскрытии блока «Выполнено ▸» (`toggleDoneList` → `all=1`). `TASKS[]` — только открытые, `DONE_TASKS[]` — выполненные (null = не загружены).

### Защита записи — safeCell_()
Все пользовательские строковые значения перед записью в Sheets проходят `safeCell_()`: значения, начинающиеся с `=`, `+`, `-`, `@`, экранируются апострофом (защита от formula injection), длина ограничена 1000 символами, числа не изменяются. Применяется в saveRow/saveAll (status/pct/comment/org/dateEnd/author) и в addTask/updateTask.

> Известный принятый риск (решение пользователя 2026-07-08): `saveRow`/`saveAll` не требуют пароля (подрядчики сохраняют без него), пароли захардкожены в script.gs и видны в публичном репозитории. Предлагались ключи в ссылках подрядчиков и перенос паролей в PropertiesService — отложено.

### Логика saveRow (построчная, для ≤20 ячеек)
1. Ищет строку по rowId в столбце A
2. Читает **только G–N** (8 столбцов) — A–F не трогает (dropdown-валидация)
3. Перезаписывает **только пришедшие поля** (status/pct/dateEnd/org/comment)
4. Дописывает автора (col N) и дату изменения (col M)
5. Пишет обратно только G–N одним запросом

### Логика saveAll (пакетная, для >20 ячеек)
1. Читает rowId (столбец A) отдельно — для построения карты
2. Читает **весь лист G–N** одним запросом — A–F не трогает (dropdown-валидация)
3. Строит карту `rowId → индекс`
4. Для каждой пришедшей строки перезаписывает только изменённые поля
5. Пишет **только изменённые строки** G–N (по changedIndices, не весь лист)
6. Возвращает `{ok, saved: <реально записано>, requested: <запрошено>}` — фронтенд предупреждает если `saved < requested`

> **Важно:** столбцы A–F содержат dropdown-валидацию Google Sheets. Запись в них вызывает "Exception: Данные не соответствуют правилам проверки". Поэтому read/write всегда только G–N (EDIT_START=7, EDIT_COLS=8). Индекс в массиве = C.X - 7.

### Защита от одновременной записи — LockService
Только `saveAll` оборачивается в `LockService.getScriptLock()` (saveRow работает с одной строкой — лок не нужен, параллельные запросы не конфликтуют):
- Второй пользователь ждёт освобождения лока (до 15 сек)
- После получения лока **читает уже обновлённые данные** → пишет поверх них
- Перезапись чужих изменений исключена

### Логика getWorkDict (обогащение данными из Факт_работы)
- Читает лист `Факт_работы` (столбцы A–K): ключ = column C (Название), значения = D(place), E(lvl1/Вид работ), F(lvl2/Группа работ), J(kp), K(factNum)
- **Защита от дублей:** если строка с тем же названием уже есть в словаре с непустыми place/lvl1/lvl2 — новая пустая запись её не перезаписывает
- Используется в `getRows` для обогащения каждой строки данными о месте/виде/группе работ
- **Кешируется через CacheService** — см. раздел ниже

### Вход через портал acons.space (2026-09-15)
Шаг 1 из `acons-server/TZ.md` §15; схема — копия Отделки/КЛАД.
- **Адреса.** Та же страница на `https://sb3.acons.space` (папка сервера `/var/www/acons/sb3`). Старый адрес github.io
  и вход по паролю работают как раньше, пока владелец не проверит новый (решение владельца 2026-09-15). Всё новое на
  странице включается только при `PORTAL_MODE` (адрес `*.acons.space`); на github.io `PORTAL_MODE=false` — пропуск не
  читается, `pp` не уходит (`portalPP()` → `undefined`, `JSON.stringify` такое поле выбрасывает), окно пароля прежнее.
- **Пропуск.** Портал открывает шахматку ссылкой `?p=<пропуск>` → страница кладёт его в localStorage `sb3_pass` и убирает
  из адреса (`?contractor=` остаётся). В бэк — полем/параметром **`pp`** (`t=` в СБ3 — метка против кэша, `p` не используем).
- **Роли портала для `sb3`:** `администратор` — режим администратора без пароля (`IS_ADMIN` из пропуска), `pp` уходит во все
  9 админских POST и в `saveRows`/`saveAll`; `просмотр` — только чтение, как без входа (окно входа не показывается — подсказка).
- **Автор** у администратора по пропуску — ФИО из пропуска: бэк сам подставляет его в `author` запроса и строк
  (столбец N «СБ3_ОБЩАЯ», «Автор» в «Поручения» и «Протоколы»); поле имени на странице — только для чтения.
- **Бэк** (`script.gs`, блок перед `clearCache`): `portalWho_` = `checkPortalPass_` (подпись HMAC-SHA256 ключом `PORTAL_SECRET`,
  код `sb3`, срок, роль) + `portalLive_` (сверка с `https://acons.space/api/portal/check`, подпись `логин|sb3|ts`, кэш 5 мин;
  сервер не ответил → доверяем пропуску). `doPost`: есть `pp` → нужен годный с ролью администратор, иначе `bad_pass`.
  GET: `pp` читают только `checkPassword` и `portalRenew`; чтение данных пропуск не проверяет. Read-only зоны, chk,
  `safeCell_`, LockService — без изменений.
- **Страница:** `bad_pass` на записи → забыть пропуск, выйти из режима администратора, сообщение (`portalPassRejected`); сама на
  портал не переходит — только по кнопкам, поэтому петли переходов нет. `renewPass` при открытии и раз в час (запрос — раз в
  сутки). «← Портал acons.space» и «Выйти» (забыть пропуск → acons.space) — только при пропуске. Окно входа на acons.space —
  «Войти через портал» (`https://acons.space/?next=sb3`) без поля пароля. Подрядчики по `?contractor=` и чтение без входа —
  без изменений, на портал не отправляются (перевод подрядчиков — §14, следующий шаг).
- **Роль «СК» убрана** (решение владельца 2026-09-15): `SK_PASSWORD` и ветка `role:'sk'` удалены из бэка, `IS_SK`,
  `.admin-sk-only`, `.sk-hidden`, `body.sk-mode` — со страницы; «Фронт открыт» — `admin-only`. Страница включает режим
  администратора только при `role==='admin'` (старый бэк на пароль СК отвечал `role:'sk'` — это теперь «неверный пароль»).

**Перед выкладкой (делает владелец / основной Claude):**
1. Script Property `PORTAL_SECRET` (тот же, что у портала) задаёт **владелец** в редакторе GAS. Без него любой `pp` → `bad_pass`,
   старый вход по паролю работает.
2. В редакторе GAS один раз запустить `authorizeServer()` и принять доступ; в журнале — ответ сервера портала с `"ok": true`.
3. Бэк — как обычно (`clasp push --force` + `update-deployment`), **раньше** страницы.
4. Страница: `scp index.html acons:/var/www/acons/sb3/index.html`; `git push` публикует ту же страницу на github.io.
5. На портале у `sb3` статус «скоро» — плитка неактивна (ссылка `https://acons.space/?next=sb3` пропуск выдаёт); после проверки
   владелец переводит в «подключена».

### Данные через сервер (с 2026-09-15)
Шаг «скорость» из `acons-server/TZ.md` §15 (решение владельца 2026-09-15). Устройство сервера — `../acons-server/CLAUDE.md`,
раздел «Шахматка СБ3».
- **Что изменилось для людей.** На `sb3.acons.space` шахматка открывается за секунды: страница читает копию данных с
  сервера acons.space, а не ждёт Google ~49 с. В строке состояния — «Загружено · … · N строк · **данные на ЧЧ:ММ**»
  (время, когда копия последний раз полностью обновилась из Google; своя отметка в копии уже есть, даже если время
  старое). На `github.io` всё как раньше — страница ходит прямо в Google, «данные на» не показывается.
- **Google остаётся источником правды.** Каждая запись (отметки, поручения, пресеты, протоколы и рассылки) идёт
  через сервер в ту же Google-таблицу и тот же бэк — отправитель писем и Telegram-бот прежние. Это важно: таблицу
  читают расчёт графика (Каскад) и Отчёт АС СБ3. Сервер после записи сразу правит у себя эти строки, затем
  уточняет их у Google. Правки прямо в таблице попадают в копию при полном обновлении — раз в 15 минут.
- **Как устроено на странице** (`index.html`, блок «ДАННЫЕ ЧЕРЕЗ СЕРВЕР acons.space»): все запросы к `BASE` идут через
  `gasFetch`. Только при `PORTAL_MODE` адрес Google заменяется на `/api/sb3` того же сайта; на github.io `gasFetch` — обычный `fetch`.
- **Когда страница сама идёт в Google:**
  - **чтение** — сервер не ответил, ответил не 2xx, HTML-страницей или ошибкой `server_error`, `google_unavailable`,
    `not_ready`, `not_found`, `bad_json`, `too_large`; «данные на» тогда не показывается;
  - **запись** — только если запрос точно не дошёл до сервера: HTTP 404/405/429/502/503, ответ
    `not_ready`/`too_large`/`bad_json`; при **обрыве сети** (сервер мог успеть передать запрос в Google) повторяются
    в Google только отметки клеток `saveRows`/`saveAll`/`saveRow` (`gasPostRepeatable` — повтор пишет те же значения);
    поручения, протоколы, рассылки, пресеты — нет: страница отвечает «Сервер не ответил — действие могло выполниться…»,
    повторное нажатие уйдёт уже прямо в Google (решение 2026-09-15, против задвоения писем и поручений);
  - сервер недоступен (обрыв или 404/405/429/502/503) — следующую **минуту** все запросы идут прямо в Google
    (`GAS_SRV_DOWN_UNTIL`), чтобы не ждать сервер на каждом.
- ⚠️ **`google_unavailable` на запись не повторять в Google.** Это значит «сервер передал запрос, но Google не ответил» —
  Google мог уже записать, повтор задвоил бы поручение или письмо. Страница показывает «Google не ответил — изменения
  могли не сохраниться. Обновите страницу и проверьте, прежде чем повторять». Не добавлять эту ошибку в списки
  `gasPostNotDelivered`.
- ⚠️ **`getRowsByIds` — копия цикла `getRows`** (`script.gs`). Меняете `getRows` (колонки `ROW_COLS`, обогащение из
  «Факт_работы», пропуск пустых строк, сортировку) — повторите в `getRowsByIds` и в acons-server (`acons/sb3.py`:
  `EXPECT`, колонки, `cell_after_write`/`date_ok` для `safeCell_`/`dateOk_`). `tests/test.js` сверяет выход
  `getRowsByIds` с `getRows` на одном листе. `getRowsByIds` только читает и есть только в `doGet`.
- **Порядок деплоя:** бэк Google → сервер acons-server → страница (`scp` на sb3.acons.space, `git push` на github.io).
- **Тесты:** `node tests/test.js` (86 тестов; раздел «Данные через сервер» — функции берутся прямо из `index.html`,
  `gasFetch` гоняется с поддельным `fetch`; раздел `getRowsByIds ↔ getRows`).

### Защита данных на фронтенде
- **Touched-флаги** (`_statusTouched`, `_pctTouched`, `_dateTouched`, `_commentTouched`, `_contractorTouched`) — поле попадает в MOD только если пользователь явно изменил его. Сбрасываются при открытии попапа.
- **beforeunload** — браузер показывает предупреждение «покинуть страницу?» если в MOD есть несохранённые изменения.
- **Ответ сервера** — если GAS вернул не JSON (HTML-редирект при сбое), показывается предупреждение «проверьте данные в таблице» вместо тихого успеха.
- **Поля дат** — ввод с клавиатуры разрешён (браузер сам не даёт сохранить неполную дату через onchange).
- **Ограничение года в дате (2026-09-10)** — допустим только диапазон `2020 … текущий год + 1`.
  Повод: подрядчик ввёл 2626 год, отчёты сломались. Реализовано в трёх местах:
  - `applyDateLimits()` (вызывается в `window.onload`) ставит `min`/`max` на поля `p-date` и `ms-date`,
    поэтому календарь браузера не даёт выбрать год за диапазоном;
  - `dateInRange()` проверяет значение перед сохранением в `savePanel()` и `msCommit()` —
    при выходе за диапазон показывается красный тост и сохранение не выполняется;
  - на бэкенде `dateOk_()` (script.gs) — последний рубеж: дата с чужим годом **не записывается**,
    её `rowId` возвращается в `badDates[]` ответа `saveRows`/`saveAll` (фронт показывает
    предупреждение), а в `saveRow` бросается ошибка. Пустая дата (очистка ячейки) разрешена.
  Границы задаются константой `DATE_MIN_Y=2020` в index.html и числом 2020 в `dateOk_()` — менять в обоих.

### Порядок колонок шахматки — инцидент 2026-09-07
Подписи «Место» (Этаж / МОП / Квартира / Лифт. холл / Лест. клетка) съехали относительно
работ под ними. Причина: в сортировке колонок (`COL_KEYS.sort` в `render()`) фиксированный
порядок задан только для трёх мест (`PLACE_ORDER`), все остальные получали одинаковый
приоритет 99 и дальше сортировались по факт. номеру работы — поэтому «Лифт. холл»
и «Лест. клетка» чередовались. Объединённая ячейка заголовка при этом рисуется на первом
появлении места, а ширина берётся по общему числу его колонок — отсюда сдвиг.

Правило на будущее: **колонки одного места и одной работы обязаны идти в COL_KEYS подряд.**
Сейчас это обеспечено сортировкой: место вне `PLACE_ORDER` встаёт по своей самой ранней
работе, работа внутри места — по самой ранней подколонке. Тот же порядок использует экспорт
в Excel (он берёт готовый `COL_KEYS`), так что шапка выгрузки чинится вместе с экраном.
